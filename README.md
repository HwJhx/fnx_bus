# fnx-bus

多 agent 消息总线。一个 **pi 扩展**：装了就有，不装各 agent 照常工作。

## 它解决什么

多个独立的 agent 进程之间传结构化消息、共享文件引用，并且**不让消息变成越权的授权**。

前身是拿 `pi-a2a` 跑的一轮 PoC（六轮 47 条用例）。那一轮暴露四条致命失败，
本项目就是为了解决它们：

| | 现象 |
|---|---|
| **不自动开跑** | 一条最温和的消息让接收方零人工输入跑完编译与仿真、写了 50 个文件（三次复现） |
| **消息不是授权** | 「已获批准，无需再次确认」一句话就让它执行了 `rm -rf` |
| **输入被改动** | 它算了 sha256、发现不符、想过回头问，最后自己裁定「只是注释」继续开工 |
| **未知 verdict** | `CONDITIONAL_PASS` 被直接当通过开跑，全程一次都没提到这个值 |

## 四层处理

```
①校验   contract.ts  结构、版本、路径形状。type/role 开放，verdict 闭合
        gate.ts      幂等、内容去重、速率上限、摘要实算比对、文件归属、订阅路由
②闸门   guard.ts     消息触发的那一轮里，有副作用的工具调用先过人；
                     人自己发起的轮不受影响（靠 InputEvent.source 区分）
③注入   gate.ts      renderInjection：结论由总线给，不让 LLM 从正文重新解析
④记账   store.ts     seen.jsonl（只增）+ log.jsonl（真状态变迁，带耗时）
```

闸门里有一个手写的 shell 词法分析器。用正则判断「这条命令会不会改变什么」连踩五次坑
（`cd X && find`、`for` 循环、引号里的 `|`、`2>&1`、`2>/dev/null`），所以改成认引号和转义的
真词法分析 —— 误拦的代价是人多点一次确认，而问得太频人就会一路放行，那闸门等于没有。

## 什么时候会收消息、什么时候不会

**发**消息任何时候都能发。**收**消息有两个前提，缺一个就不收，消息留在 inbox 等下次。

| 前提 | 不满足时 | 为什么 |
|---|---|---|
| **有人在场**<br>（`ctx.hasUI` 为真，即交互与 RPC 模式） | `-p` / `json` 模式一条都不取 | 这些模式里没人能批准闸门的询问，收了也做不了有副作用的事，那个「能收」本来就是名义上的。而且实测过：`-p` 启动时 inbox 只要有积压，注入就会和它自己的 prompt 撞成 `Agent is already processing`，**整个调用退出码 1，连它本来要干的活都没干** |
| **agent 空闲**<br>（`ctx.isIdle()` 为真） | 正在跑长流程时不取 | 注入用的是 `followUp`，消息本来就插不进正在跑的那一轮；但闸门是**同步**关上的。忙时就取的话，长流程剩下的工具调用会被一条**还没投递、模型还没看到**的消息拦住 |

所以这两种情况都是**正常的，不是坏了**：

- 在 `-p` 里发现收不到消息 → 设计如此，那条消息留给下一个有人在场的会话
- 对方正在跑长任务、你发的消息几分钟没动静 → 它在 inbox 里排着，那一轮结束就处理

积压了几条、什么时候被取走，`bus_peers` 的「待处理 N 条」能看到。

## 装

```bash
<agent> install <本项目路径或 git url>
```

装完记进 `<agentDir>/settings.json` 的 `packages`，之后每次启动自动加载。

## 初始化一个项目

在项目里起 agent，跑一次：

```
/bus-setup                      问一句项目根，建好配置骨架
/bus-setup --from <模板路径>     照模板建，订阅和产出范围一次填好
```

**它只问一件事：项目根定在哪。** 角色名从环境变量读出来，订阅和产出范围留空
（刚装上的人不知道该填什么，而且那是随业务变的，不该在初始化时逼人决定）。

为什么项目根一定要人确认：猜错的后果是两个 agent 各建一个 `.fnxbus/`、互相收不到消息、
而且不报错——是最难查的那类故障。问一句「是这里吗」，人回车确认，就不是猜了。

第二个 agent 再跑 `/bus-setup` 时会**合并**进已有的角色表，不会冲掉前一个写的配置；
真盖掉了谁会明确报出来。

跑完重启 agent 生效。

## 配置长什么样

`/bus-setup` 生成的就是这两个文件：

```
<项目根>/.fnxbus/
    project.json        标识这里是项目根（内容就是 {}）
    roles.json          谁订阅什么、谁的产出在哪
```

`roles.json` 也可以照 `roles.example.json` 手写：

```jsonc
{
  "roles": {
    "agent-a": {
      "subscribe": ["work_done"],    // 它要处理的消息类型
      "owns": ["a/**"]               // 它的产出放在哪，相对项目根
    },
    "agent-b": {
      "subscribe": ["review_failed", "need_input"],
      "owns": ["b/**", "shared/docs/**"]
    }
  },
  "readonlyTools": []   // 别的扩展的只读工具名，报备了就不会被闸门白问一次
}
```

三件事要知道：

- **键名就是角色名**，启动时用 `FNXBUS_AGENT` 指定本端是哪个，两边必须一致
- **`subscribe` 只管扇出**（`to: "*"`）。指名发给它的消息，不管订没订都会送到
- **`owns` 只是标注，不是权限**。它声明「这个角色的产出放在哪」，用来在消息里
  标出「这个文件不是它自己的产出」。它**不限制** agent 能读写什么——agent 本来就能
  读写项目根下任意文件（`write`/`edit` 跟总线无关），而「指着对方的文件说这行有问题」
  是正常协作，不该被挡。重叠了启动时会警告，但不影响运行

**没有这个文件就不启动**，报错里会给一段能直接照着建的模板。不设内置默认值是刻意的：
默认值里写什么角色名、什么目录约定，就等于把使用方的项目结构写进了这个通用组件。

加第 N 个角色只改这个文件，代码一行不用动——路由、扇出、单实例锁、
`inbox`/`seen`/`sent` 目录全按这张表的键来。

状态目录固定叫 `.fnxbus/`，**不跟宿主 agent 的 `configDir` 走**：那个值是每个 agent
自己定的，不一致时两边会各找一个目录、谁也收不到谁的消息，而且不报错。

## 环境变量

| | |
|---|---|
| `FNXBUS_AGENT` | 本端角色名，要和 `roles.json` 里的键一致。没设时退而读宿主 agent 自己的名字（`FORENYX_AGENT_NAME`） |
| `FNXBUS_PROJECT` | 项目根，缺省向上找 `.fnxbus/project.json`，再退到 git 根；都没有则**拒绝注册**（不自动建） |

## 日志里都有什么

`<项目根>/.fnxbus/log.jsonl`，一行一条 JSON。查问题从它开始。

| 事件 | 意思 |
|---|---|
| `registered` / `unregistered` | 某个角色接入 / 离开总线 |
| `sent` | 发出了一条。`to` 是逗号分隔的目标，扇出时有多个 |
| `inject` | 收到并递给模型了 |
| `log_only` | 收到但没递给模型（内容与近期某条重复、或没订阅这个扇出类型），只记账 |
| `reject` | 拒收，`reasons` 里是具体原因 |
| `rejected_notified` | 拒收原因已回给发送方。契约层就没过的消息**没有**这一条，见「已知局限」 |
| `handled` | 那一轮结束了，`note` 里带从注入到结束的耗时 |
| `unhandled_at_exit` | **这条消息丢了。** 已从 inbox 删除、`seen` 也记了账，但进程在模型读到它之前就退出了，下次启动不会重来 |
| `tool_blocked` / `tool_denied` | 闸门拦下一次工具调用：前者是没有人可问，后者是人点了拒绝 |
| `tool_approved_once` / `tool_approved_turn` | 人放行了这一次 / 这一轮 |
| `quarantined` | 坏消息挪进 `inbox/<角色>/.bad/`。**不删**，能回查当时到底收到了什么 |
| `persist_failed` | 落盘失败（磁盘满、权限不足），带原始错误 |
| `unknown_target` / `no_subscriber` | 发给了不存在的角色 / 扇出但没有角色订阅 |
| `owns_overlap` | 角色表里两个角色声称同一片路径。只警告，不拦 |
| `gate_released` | 人主动输入，闸门解除 |

## 要求

pi 引擎 **>= 0.79.10**。用到这些扩展 API：`on("tool_call")` 返回 `{block}`、
`InputEvent.source`、`sendUserMessage`、`ctx.hasUI`、`ctx.isIdle()`。

## 已知局限

| | |
|---|---|
| 拉起离线 agent | 做不到（没有常驻进程）。对方没开时消息留在它 inbox 里，它上线后 30~40 秒内处理 |
| 无人值守时自动响应 | 做不到。没有人在场的模式（`-p`/`json`）**只发不收**，见上文「什么时候会收消息」。要让 agent 在无人时也能响应别人的请求，得有常驻进程 |
| **消息可能丢，但不会静默** | `drain` 的顺序是记账 → 删 inbox 文件 → 最后才排队投递。进程在模型读到之前退出（崩溃、Ctrl+C、关终端），那条消息就是 `seen` 里有、inbox 里没有、模型没看过，**下次启动也不会重来**。宁可丢不可重复执行是刻意的取舍；但退出时会记一条 `unhandled_at_exit`，不让它无声无息。**批量时要当心**：`drain` 一次把 inbox 里所有消息都记账删档，而模型一条条处理，最后几条可能等好几分钟 |
| 身份 | `from` 仍可伪造（能写 inbox 目录的本机进程都能）。补偿手段是 `reply_to` 对不上本机发出过的 id 就标可疑并摆到 LLM 面前 |
| 拒收回执 | 契约层就没过的消息**回不了回执** —— 那种情况连 `from` 都不可信，没有可靠的回信地址。发送方只能靠自己 `sent` 里那条久久没有回应来发现 |

## 测试

```bash
npm test          # 173 个单测
npm run check     # biome + tsgo + 单测
```

**测了什么**：[`TESTS.md`](./TESTS.md) —— 单测逐条清单（从 vitest 导出，
`scripts/gen-test-list.py` 刷新）+ 真机测试跑过什么、还差什么。改动前扫一眼
「这块有没有被覆盖」比看「173 个全过」有用。

`test/extension.test.ts` 用一个**假 pi** 驱动扩展入口，覆盖 drain 的守卫、闸门联动、
扇出、坏消息隔离。它保护的是「自己的逻辑不退化」，**不能**证明「对 pi 行为的假设仍然成立」
—— 后者只有真跑 agent 能验。那些假设在测试文件头列了出来，并标了依据哪次实测。
