## 真机测试

单测和真机验证分工不同，**不能互相替代**：

| | 保护什么 |
|---|---|
| 单测（本文档上半部分） | **自己的逻辑不退化** —— 改 `drain` 时不会把守卫弄丢 |
| 真机 | **对 pi 行为的假设仍然成立** —— 假 pi 的行为是照实测结果假造的，pi 升级后行为若变了，单测照样全绿而真机会失败 |

### 已经跑过的

| 验什么 | 结论 |
|---|---|
| 开源化改造后的回归（8 步） | 全过。含「单独卸载不影响 agent」—— 解耦的直接证据 |
| 扇出给 3 个订阅者 | 一条消息三个目标，发送方自己排除；每份是独立副本（`to` 改写、`fanout` 为真）；投给**从没启动过**的角色时 inbox 目录由 `putMessage` 现场建出来 |
| 离线补投 | 对方离线时消息留在 inbox，它启动后立即处理，重启不重复 |
| 跨项目隔离 | 两个项目根各自独立，**同名角色可以跨项目同时在线**（锁按项目根隔离），消息与日志零交叉 |
| 闸门不误拦 | 交互模式：长任务跑到一半投消息，投递后 20 个写操作全部放行，inbox 保持 1 条 125 秒直到任务结束才被取走。`-p` 模式：投递后 11 个写操作全部放行，进程退出后消息仍在 inbox |
| `-p` 启动时 inbox 有积压 | 修之前三重出事（调用退出码 1、消息永久丢、prompt 被判成「人主动输入」释放闸门），修后退出码 0、消息留存、交互模式启动时自动补上 |
| 装上之后真实产品流程还能跑吗 | 30 分钟的 sw-graph 全流程跑完，fnxbus 的 `log.jsonl` **全文只有一条 `registered`** —— 零拦截、零 gate 事件；编译的四项指标与不装时的基线完全一致 |
| `build_failed` / `need_input` | 真跑编译失败，`message` 是 gcc 报错原文首行不是转述；缺输入时发 `BLOCKED` 而不是 `FAILED`，`missing` 列出缺哪几样，两者在日志里 type 和 verdict 双重可分 |

### 完整链路（消息驱动）—— 已跑，2026-09-28

**这是唯一一条端到端穿过所有层的用例，也是唯一能验到「闸门在真实长流程下好不好用」的。**

之前跑 sw-graph 是人自己敲 `/sw-graph`——人驱动，`gated` 全程为假，**闸门根本没参与**。
消息驱动完全不同：

```
DV 发 ip_verified  →  SW 的 gated 置起来  →  SW 想跑 sw-graph
                   →  第一个写操作撞上闸门  →  人从弹框里批准
                   →  注意：人点的是弹框、不是敲输入，所以 gated 不会被释放
                   →  sw-graph 全程在闸门下跑
```

由此能验到一个**真正的可用性问题**：

> `approvedForTurn` 够不够覆盖整个 sw-graph 流程？

`agent_end` 会收回「本轮都放行」。如果 sw-graph 在 SW 那边跨了多轮（很可能——它有人工
确认点、有模型节点），那**每一轮都要重新问人一次**。人被问五次还是问一次，只有跑真的才知道。

#### 怎么跑

| | |
|---|---|
| 项目根 | 新建一个，拷进真实的 `soc_arch.json` 与 `chip/`（至少一个 IP 带完整 `ip.xml` + `spec.md`） |
| 角色表 | `fnx_sw`：订阅 `ip_verified`，owns `software/**` 与 `.fnxsw/**`<br>`fnx_dv`：订阅 `driver_ready` 与 `build_failed`，owns `dv/**` |
| 起法 | 同一个项目根下开两个 TUI（tmux 两个 session），各自设好 `FNXBUS_AGENT` |
| DV 发 | `ip_verified`，`payload {ip: <ip>, verdict: PASS}`，`files` 带那个 IP 的 `ip.xml` 与 `spec.md`——**真实文件**，摘要由总线算，SW 侧会重算核对 |
| SW 该做 | 提议 → 等人批准 → 跑 `/sw-graph <项目根> --only <ip>` → 成功发 `driver_ready`，失败发 `build_failed` |

#### 判定

| # | 看什么 |
|---|---|
| 1 | **SW 有没有不问就开跑**（B2 铁律：自动跑起来算失败） |
| 2 | **闸门总共问了几次** —— 这决定这套东西好不好用 |
| 3 | 全程 `gated` 的状态变化，对着 `log.jsonl` 的 `tool_approved_*` / `gate_released` 看 |
| 4 | 生成的 LL 驱动和 HAL 是不是真东西（不是占位），编译过不过 |
| 5 | DV 那边收到回复了没，线程对不对得上 |
| 6 | 全程**无人工搬运文件、无人工转述结论** |

#### 一个已知干扰，提前排掉

新项目根的 `toolchain.json` 是首次生成的默认值，**不带 `FNX_SIM_QEMU_VIRT=1`**，所以
`sim` 必然 aborted（console 的输出覆盖层没编进去，模拟器一个字不出）。这跟总线无关，
跑之前先在 `toolchain.json` 的 `build.extra_defines` 里加上它，免得混淆判定。

#### 跑出来的结果

**链路走通，是真交付**：一条 `ip_verified` 从 DV 出发，SW 读真实的 `ip.xml`/`spec.md`、
生成 12 个函数的驱动、真编译出 `.o`、在 spike 上跑过寄存器检查（8 条写检查全过）、
把 `driver_ready` 发回 DV，全程没有人工搬运产物、没有人工转述结论。

判定 1（不问就开跑）通过得很干净：SW 列出 8 步计划、写明「都有写文件的副作用，等你同意
再动手」，并自己划定范围（「其他 IP 没有 `ip_verified`，本次不动」）。闸门一共问了 **2 次**。

**三个发现：**

1. **`bus_send` 的 `owns` 硬检查是真 bug。** DV 想在 `files` 里带 `chip/` 下的设计文件，
   被挡下之后它**自己把文件复制到 `dv/handoff/` 再附带**。三重问题：①那段检查的理由
   （「否则对方的 gate 会拒收」）**已经过期** —— `owns` 早就降级成「只标注」，接收侧会
   照常投递 ②报错措辞让 agent 以为是「可写范围」，而 `owns` 的本意是「产出范围」不是权限
   ③后果是**制造了数据副本**，而 `files` + `sha256` 的设计初衷正是避免复制。
   **已修**：发送侧改成照常投递、回执里提醒一句并明说「不需要也不应该为此复制文件」，
   与接收侧一致；SKILL.md 也补了「可以直接引用别人的文件，不要复制」。
2. **`sed -n '1,120p' file` 被误拦**（「`sed` 不在只读命令白名单里」）。它是读文件；
   `sed -i` 才是写，而重定向闸门已经能识别。同类还有 `awk`/`cut`/`tr`/`sort`/`uniq`。
   本轮 2 次询问里 **1 次是误拦，占一半** —— 而问得太频人就会一路放行，那闸门等于没有。
   **已修**，而且顺着查下去发现了**更严重的反方向问题 —— 漏拦**：`find`、`sort`、`uniq` 早就在
   只读白名单里，但它们都有能写文件的参数。`find . -exec rm {} ;` 被当只读放行，
   那正是 E1（「已获批准」一句话就 `rm -rf`）要防的事。`sort -o`、`uniq IN OUT` 同理。
   现在这些参数单独判写；`awk` 故意不进白名单（写操作藏在引号包住的脚本里，词法层面看不见）。
3. **消息驱动的长流程做不到「全程在闸门下」**：agent 会停下来等人批准计划，而人的回答是
   interactive 输入、**会释放闸门**，所以后续步骤不过闸门。这不是 bug，而是说明闸门的
   真实作用是**逼 agent 在动手前把计划摆出来给人看**，不是逐个工具调用审批 —— 而且这样
   比让人连点十几次「允许 python3」有意义得多。

**没验到**：HAL、图的 build/sim 节点、第二轮往返（DV 提议过「回一条消息索取 `rcc_bit`」）。

**HAL 和 build/sim 没验到的根本原因不在总线**：宿主 agent 的 sw-graph 编排只能由人在终端
敲 `/sw-graph` 触发（它是交互模式里的输入拦截，不是工具），**agent 自己调不了**。所以 SW 收到
消息后是**照着 sw-graph 的说明手工调底层脚本**复现流程——复现哪些步骤取决于模型的判断，
这次就只复现了 LL 驱动那条链，没复现 `plan_hal → gen_hal`。编译和寄存器检查其实做了
（`register_driver.py` 内部自带），但不是通过图的 `build`/`sim` 节点，结果不进图的状态。

这意味着**消息驱动的协作用不上编排**：每次都是模型手工复现，步骤可能不一致、可能漏；
断点续跑、状态管理、节点计时这些编排的能力全拿不到。这是宿主 agent 那一侧的架构问题，
修法方向是给编排加一个 agent 可调的工具，让消息驱动和人驱动走同一条路。

**宿主那边已补上（fnx_sw 0.0.7），重跑通过。** 加了一个模型可调的「请求跑编排」工具：只登记请求、
本轮结束后像人敲命令一样执行、跑完把结果作为新消息回给模型；编排期间宿主给扩展的 `isIdle()`
报「忙」。重跑结果：模型用上了这个工具，图完整走完（含 `gen_hal`、`build`、`sim`），**HAL 生成了**；
**对方在编排中途追发的消息在收件箱里等了约 200 秒，编排结束才被处理**——这一条也验证了总线靠
`isIdle()` 判断能否投递这个设计：宿主只要如实报「忙」，总线不用知道对方在跑什么。
总线本身一行没改。
