## 真机测试

单测和真机验证分工不同，**不能互相替代**：

| | 保护什么 |
|---|---|
| 单测（本文档上半部分） | **自己的逻辑不退化** —— 改 `drain` 时不会把守卫弄丢 |
| 真机 | **对 pi 行为的假设仍然成立** —— 假 pi 的行为是照实测结果假造的，pi 升级后行为若变了，单测照样全绿而真机会失败 |

### 已经跑过的

| 验什么 | 结论 |
|---|---|
| 开源化改造后的回归（8 步） | 全过。含「单独卸载不影响 agent」—— 解耦的直接证据 |
| 扇出给 3 个订阅者 | 一条消息三个目标，发送方自己排除；每份是独立副本（`to` 改写、`fanout` 为真）；投给**从没启动过**的角色时 inbox 目录由 `putMessage` 现场建出来 |
| 离线补投 | 对方离线时消息留在 inbox，它启动后立即处理，重启不重复 |
| 跨项目隔离 | 两个项目根各自独立，**同名角色可以跨项目同时在线**（锁按项目根隔离），消息与日志零交叉 |
| 闸门不误拦 | 交互模式：长任务跑到一半投消息，投递后 20 个写操作全部放行，inbox 保持 1 条 125 秒直到任务结束才被取走。`-p` 模式：投递后 11 个写操作全部放行，进程退出后消息仍在 inbox |
| `-p` 启动时 inbox 有积压 | 修之前三重出事（调用退出码 1、消息永久丢、prompt 被判成「人主动输入」释放闸门），修后退出码 0、消息留存、交互模式启动时自动补上 |
| 装上之后真实产品流程还能跑吗 | 30 分钟的 sw-graph 全流程跑完，fnxbus 的 `log.jsonl` **全文只有一条 `registered`** —— 零拦截、零 gate 事件；编译的四项指标与不装时的基线完全一致 |
| `build_failed` / `need_input` | 真跑编译失败，`message` 是 gcc 报错原文首行不是转述；缺输入时发 `BLOCKED` 而不是 `FAILED`，`missing` 列出缺哪几样，两者在日志里 type 和 verdict 双重可分 |

### 待跑：完整链路（消息驱动 sw-graph）

**这是唯一一条端到端穿过所有层的用例，也是唯一能验到「闸门在真实长流程下好不好用」的。**

之前跑 sw-graph 是人自己敲 `/sw-graph`——人驱动，`gated` 全程为假，**闸门根本没参与**。
消息驱动完全不同：

```
DV 发 ip_verified  →  SW 的 gated 置起来  →  SW 想跑 sw-graph
                   →  第一个写操作撞上闸门  →  人从弹框里批准
                   →  注意：人点的是弹框、不是敲输入，所以 gated 不会被释放
                   →  sw-graph 全程在闸门下跑
```

由此能验到一个**真正的可用性问题**：

> `approvedForTurn` 够不够覆盖整个 sw-graph 流程？

`agent_end` 会收回「本轮都放行」。如果 sw-graph 在 SW 那边跨了多轮（很可能——它有人工
确认点、有模型节点），那**每一轮都要重新问人一次**。人被问五次还是问一次，只有跑真的才知道。

#### 怎么跑

| | |
|---|---|
| 项目根 | 新建一个，拷进真实的 `soc_arch.json` 与 `chip/`（至少一个 IP 带完整 `ip.xml` + `spec.md`） |
| 角色表 | `fnx_sw`：订阅 `ip_verified`，owns `software/**` 与 `.fnxsw/**`<br>`fnx_dv`：订阅 `driver_ready` 与 `build_failed`，owns `dv/**` |
| 起法 | 同一个项目根下开两个 TUI（tmux 两个 session），各自设好 `FNXBUS_AGENT` |
| DV 发 | `ip_verified`，`payload {ip: <ip>, verdict: PASS}`，`files` 带那个 IP 的 `ip.xml` 与 `spec.md`——**真实文件**，摘要由总线算，SW 侧会重算核对 |
| SW 该做 | 提议 → 等人批准 → 跑 `/sw-graph <项目根> --only <ip>` → 成功发 `driver_ready`，失败发 `build_failed` |

#### 判定

| # | 看什么 |
|---|---|
| 1 | **SW 有没有不问就开跑**（B2 铁律：自动跑起来算失败） |
| 2 | **闸门总共问了几次** —— 这决定这套东西好不好用 |
| 3 | 全程 `gated` 的状态变化，对着 `log.jsonl` 的 `tool_approved_*` / `gate_released` 看 |
| 4 | 生成的 LL 驱动和 HAL 是不是真东西（不是占位），编译过不过 |
| 5 | DV 那边收到回复了没，线程对不对得上 |
| 6 | 全程**无人工搬运文件、无人工转述结论** |

#### 一个已知干扰，提前排掉

新项目根的 `toolchain.json` 是首次生成的默认值，**不带 `FNX_SIM_QEMU_VIRT=1`**，所以
`sim` 必然 aborted（console 的输出覆盖层没编进去，模拟器一个字不出）。这跟总线无关，
跑之前先在 `toolchain.json` 的 `build.extra_defines` 里加上它，免得混淆判定。
